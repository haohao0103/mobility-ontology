## 3. 补算结果：公理（状态机）与层级（分类归属）

### 3.1 口径（分母定义与来源）

| 项 | 定义 | 来源 |
|---|---|---|
| 公理分母 | Stage A 中与人工基线**精确名匹配**的类 25 个；其中 LLM 声明了 `state_machine` 的 14 个作"声明率"分母 | `tools/_out/blindtest_raw/20261125_201223_{A,B}*.txt` |
| 人工侧状态集 | 每类 `statuses`（`C()` 第 6 参数） | `ontology/domains_02_capacity.py`（98 类） |
| 层级人工侧 | 每类 `_group`（6 个域组：vehicle/driver/carrier/subcontract/maintenance/fuel） | 同上 |
| 剔除 `OTHER` | prompt 要求 `states` 末尾带 `"OTHER"` 兜底态，人工侧无此态 ⇒ 不剔除会系统性压低重合度 | `tools/modeling_prompt.md` |

**两处口径修正**（先验口径再引用数字，避免低估或高估模型）：

1. **初态用两档口径**：A 集合口径 `initial ∈ 人工 statuses`；B 位置口径 `initial == 人工 statuses[0]`。
   位置口径的依据：在 8 个**显式声明 `state_machine` 段**的类上实测
   `statuses[0] == initial` 命中 **7/8**。
2. **终态只用集合口径**，不用 `statuses[-1]`：同组实测 `statuses[-1] == terminal` 仅 **4/8**
   （terminal 是"业务终点"而非"最后一个状态"，如 `Settlement` 的 terminal=ON_HOLD、
   `Quote` 的 terminal=SUPERSEDED）。

### 3.2 数字（诊断口径，不改已注册判据）

| 指标 | 结果 | 分子/分母 |
|---|---|---|
| state_machine 声明率 | **56.0%** | 14 / 25 匹配类 |
| 初态命中（集合口径） | **14.3%** | 2 / 14 |
| 初态命中（位置口径） | **14.3%** | 2 / 14 |
| 终态命中（集合口径） | **21.4%** | 3 / 14 |
| 状态集精确一致 | **0.0%** | 0 / 14 |
| 状态集 Jaccard 均值 / 中位 | **0.1429 / 0.0** | 14 个声明类 |
| 人工状态覆盖率均值 | **20.4%** | 声明类上的交集/人工状态数 |
| 状态全集 Jaccard | **0.1075** | 人工 57 态 vs LLM 46 态 |
| 层级（Stage A 带 `group` 的类） | **0 / 113（0.0%）** | Stage A 模板未要求 `group` ⇒ **本轮不可测** |

证据：`docs/blindtest-evidence/blindtest_axiom_20261125_201223.json`（含逐类明细）。

### 3.3 结论边界（必读，防止过度解读）

- **公理 = 测了，且极弱**：声明率仅 56%（11/25 匹配类根本没写状态机）；写了也基本不命中
  （状态集精确一致 0%、初态命中 14.3%、终态 21.4%）。**但 n 极小**（声明类仅 14 个、命中数 2~3），
  这是**强方向性证据，不是稳健统计**——不据此对"公理生成能力"下总体断言。
- **层级 = 未测，不是"差"**：`group` 字段 0/113 的直接原因是 Stage A 模板没要求输出 `group`，
  模型无从给。**不能据此说"模型不会建层级"**；要测必须重跑 Stage A（模板加 `group` 要求）。
- **属性 68% 是条件准确率**：分母是"匹配类中两边都有的属性"（50 条），即**只在捞对的类上评**；
  类召回 25.5% 意味着约 3/4 的类没被捞对、那些类的属性完全没被计分。
  ⇒ 长文说"属性建模也是弱项"，我方**不能**用 68% 反驳，因为口径不可比。

## 4. 交叉验证结论

### 4.1 印证

1. **L1 三弱项成立且我方实测同向**：属性 68%（条件口径，未达 85% 判据）→ 弱；
   公理（声明率 56%、状态集精确一致 0%）→ 极弱；层级 → 未测但模型零输出。
2. **L5 双级任务同构**：长文说"捞词行、造本体不行"（CQ2Term→CQ2Onto），我方 Stage A（捞类清单）
   / Stage B（补属性与类型）正是同一分解。实测**捞词行更弱**：类召回 25.5%（精确名）/
   46.9%（语义对应诊断口径）明显弱于属性条件准确率 68% ⇒
   **先捞类、再补属性**这个顺序在本域成立，但第一段是瓶颈。
3. **L4 星标结构**：§5 独立复核成立。

### 4.2 长文没直接说、但我方数据补上的一条

**"层级"在我方口径里不是继承制** ⇒ L2（"推理补不回层级"）对我方影响比文章设想的小：
我方层级载体是 `primary_aggregate` + `labels` + 35 个 `object_type_groups`（500 成员），
**不是 subclass 闭包**；公理载体是 16 条 `rules`（when/judge AST）+ 8 个 `state_machines` + 15 个 `actions`。
推理层不需要"父子关系建对"才有意义。
**但代价是**：这 35 组与 8 个状态机目前**全靠人工维护**，模型一个都不产（group 0/113）⇒
我方在这条上的现实缺口不是"模型建错了层级"，而是**"层级与状态机尚未进入自动产出的评估范围"**。

### 4.3 不适用于我方（不套用）

- **L6 本体税 / 10–15 数据源盈亏线**：面向"企业买本体做异构数据集成"的成本结构。
  我方是**本体工程工具链生产方**（提议 → 确定性门禁 → 裁决 → 人审 → 编译 → 校验 → pin），
  成本结构完全不同（我方的成本项是"人工建模工时"与"人审吞吐"，不是"本体运维税"）。
  强行套用会得出错误的定价结论 ⇒ 记为**不适用**，不是"不采纳"。
- **"星标 = 价值"**：长文自己反对这个读法（§5.1 实证：Graphify 星最多但只做代码/文档 → 图谱），
  我方台账同样坚持**能力核对（文件:行号）而非星标排序**。本次实测星标只是把文章的数字**验一遍**。

## 6. 可借鉴 / 不借鉴（对我方）

**可借鉴（按性价比排序）**

1. **"本体是尺子，不是发动机"→ 我方定位表述**（零成本）：我方不做决策生成，只提供**可校验的尺子**
   （`validate_semantic` 逐键 diff + `payload_sha256` pin fail-closed）。
   长文"先买校验"的取向与我方"校验先于发布"路线同向——**这条是我方已有的差异化，不是新增**。
2. **三弱项分项应进盲测常规项**（低成本，本轮已落地补算工具）：今后盲测固定测三项
   （属性 / 层级 / 公理），避免再次出现"判据只覆盖一项、结论被当成整体能力"的误读。
3. **`semantica` 的"四路确定性推理 + 不确定挡在本体外"**（中成本，待评估）：
   与我方"推导事实带置信度与来源、冲突以断言为准"的取向一致，可作为**规则层输出格式**的参照；
   不搬其推理引擎（我方 16 条 rules 是业务规则，不是逻辑推理）。
4. **utopia 双时钟**（中成本，待评估）：世界何时为真 vs 系统何时开始相信 ⇒
   我方 `effective_from` / `version` 字段已具备半个双时钟雏形，
   但**没有"系统何时知道"的第二时间轴**，在时点回放与对账场景可能缺口。
5. **`operational-ontology` 的"业务对象 / 属性 / 动作 / 权限"四件事结构**（低成本，待评估）：
   我方现为 对象 / 关系 / 状态机 / 动作 / 规则 五段，**缺"权限"维度**；
   若客户要 RBAC 与本体对齐，这是明确缺口。

**不借鉴**

- 图谱检索增强整类（Graphify 153k 星那一类）：做的是"从**已有代码/文档/schema** 反向捞实体与关系"，
  与我方"从业务口语建模"不是同一层。我方的 `fact_store` 仍是 `seed.py` 演示数据，
  真实数据源接入尚未开始（P2 断言溯源蓝图已备）⇒ **现在抄这类等于抄上游**。
- 本体税/盈亏线数字（§4.3）。
- 以星标排序决定借鉴优先级。
