# 第三方实现评审清单

> 评审的目标**不是**挑出"最弱的属性图实现"，而是确认：
> **这是一个认真做的、代表该路线真实形态的实现**。
> 把它写得比本体弱 → 基准不中立；把它写得比本体强 → 基准也不中立（那说明用例有偏）。

## A. 独立性（不满足则直接退回）

- [ ] 实现没有 import 作者私有包（`freight` / `semantic_layer` 等）
- [ ] 实现没有读取 `manifest.json` / 任何期望值文件
- [ ] 实现是**从零写的**：作者声明未参考 `implementations/` 下的内置参考实现
- [ ] 实现可独立运行：只依赖标准库（或已声明的第三方库）

## B. 完整性（实现有没有把题目做完）

- [ ] 六个契约方法都实现了，没有 `NotImplementedError` 残留
- [ ] 每个用例都有实质回答（不是返回空 dict 或恒 0）
- [ ] `apply_change` 真实落盘改动（不是空实现后声称改过）
- [ ] `restart_required` 如实声明：改配置/代码后若需要重启才能生效，必须为 True

## C. 公平性（这是最容易出问题的地方）

- [ ] **参数该放哪就放哪**：作者认为该配置的就配置，该在代码里的就在代码里——
      **不要按我们的偏好来**（我们的本体路线是"全放声明"，那是我们的偏好，
      不是属性图路线的最佳实践）
- [ ] 车型费率、免费分钟、块大小等参数，**该有几份副本就有几份**：
      真实项目里"同一语义写两遍"很常见，**刻意消除它会让这条路线变得比真实情况更强**
- [ ] 金额上限、状态前置这类语义，用**你认为合适的方式**表达（配置项 / 代码分支 /
      查表），不要为了对齐我们的字段名而硬套
- [ ] 没有为了"多对几个用例"而加入特殊分支（针对具体 case id 的硬编码一律拒绝）

## D. 可复现与可复核

- [ ] 同一份数据多次运行结果一致（评测器会为每个用例准备独立工作区）
- [ ] 变更后重新取数得到新结论（评测器会重新加载你的实现）
- [ ] 实现里没有依赖时间戳、随机数、网络等不可控因素

## E. 作者自述（必填，评审会看）

请在 PR 里写清楚：

1. 费率参数放在哪、金额上限怎么表达、车型怎么参与计算；
2. 你在实现中遇到的**判断题**及你的选择与理由；
3. 你认为本协议/用例**不公平**的地方（我们承诺会讨论并可能改基准）；
4. 你认为这条路线**最难**的部分是什么。
