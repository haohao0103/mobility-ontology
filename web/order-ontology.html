先拆成四个问题货拉拉的每一单，都能这么问一遍

Q1 / 名词

有哪些「东西」？

不是表和字段，是业务里真实存在的物件。每个都定一个全公司唯一的身份。

货主 · 订单 · 运单 · 司机 · 车辆 · 费用项 · 结算单 · 发票 · 异常工单
Q2 / 关系

它们怎么「认识」？

不是两张表能 JOIN，而是「这单是谁派的、这车是谁的」。关系要带时间和来源。

运单 来自 订单　司机 承运 运单
费用项 汇入 结算单
Q3 / 规矩

什么「不能」做？

现在散在十几个服务的 if-else 里，各写一遍。本体把它们收到一处说清楚。

没装货 不能改派；没回单 不能结算；
已入账 只能冲正
Q4 / 动作

能「做什么」？

带参数、带权限、带校验、带留痕的写操作——不是一句 UPDATE。

展开关系，找差额

多出的 38 元 = 等候费 25 + 高速费 13，其余 5 项与预估一致

费用项 × 7等候费 +25高速费 +13其余 5 项一致
3

取证据，不取结论

司机 09:12 到达装货点，10:05 完成装货——等候 53 分钟，超过 30 分钟免费时长；高速费有 ETC 扣费记录

每条证据带：来源系统 · 时间戳 · 版本号
4

套规矩

等候费按每 5 分钟 2.4 元计：[(53-30)/5] × 2.4 ≈ 12 元… 实际收取 25 元 → 计费异常，多收 13 元

规矩不是散落的 if-else，而是对象上可复用、可解释的声明式校验。
5

提动作，人确认

dispute_charge 发起费用申诉 → 客服核定 → waive_charge 减免（需审批） → reverse_entry 冲正已入账部分

动作带参数、权限、前置校验和审计，不是一句 UPDATE 改库。
6

回读业务事实

结算单金额 -13、发票金额同步、货主收到解释、审计流留下一条完整链路

返回的不是「成功」，是「影响了哪 3 个对象、现在什么状态、下一步能做什么」。

07

最小闭环怎么走不用一上来就建平台

选一个真实问题，四步走完，比画一张大图有用得多。

STEP 1

定身份

先把运单号定成跨系统唯一业务主键，把各系统的叫法对齐。

STEP 2

定关系

只做三条：来自订单、指派司机、产生费用项。每条带时间和来源。

STEP 3

定规矩

把散落的 if-else 写成声明式校验：未装货不可改派、缺回单不可结算。

STEP 4

定动作

先做只读诊断（查费用、查资质），跑通再上写回（改派、冲正）。

一句话收尾：数仓把事「记下来」，本体把事「讲明白」。前者回答「有多少」，后者回答「是什么、和谁有关、能怎么办」。
说明：文中系统名、动作名与计费规则均为示例结构，用于说明建模思路，实际以公司业务定义为准。本体层不重复实现写入逻辑，只统一「对象 / 前置条件 / 权限 / 幂等 / 留痕」的约定。

Object Set 查询台组合语义 · 快照一致 · keyset 分页

Object Set 不是简单列表接口：set 支持 from / where / followLink / union / intersect / subtract 组合；page 使用签名 token 做 keyset 推进，同一查询跨页共享 set_id 与 snapshot_id，并集必须与一次性查询完全一致。下面每次操作都会调用真实后端并现场断言契约。

查询构造器 + 分页契约验证

同一 filter / orderBy 下逐页取数，断言“不重不漏、set 不变、snapshot 不变、next_page_token 只出不进”。

POST /freight/object-set/query
选择类型后运行，右侧会显示真实请求与响应。
