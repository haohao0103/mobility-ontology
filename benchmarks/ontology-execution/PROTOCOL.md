# 接入协议 · ontology-execution v0.1.0

> 本协议规定：实现方要提供什么、评测方怎么判、什么条件下结论才算数。
> **协议变更需要走版本号**：manifest 里的 `version` 变更即视为破坏性变更。

## 1. 接口契约

每个实现提供一个类（模块里导出 `IMPL` 即可，评测器按这个约定发现它）：

| 方法 | 签名 | 返回 |
|---|---|---|
| 差异归因 | `q1_diff(waybill_id="WB20261105001") -> dict` | `quoted_total` / `actual_total` / `diff_total` / `waiting_expected` / `waiting_over` / `explain` / `audit` |
| 规则应计 | `q2_waiting(waybill_id="WB20261105001") -> dict` | `waiting_expected` / `waiting_over` / `explain` / `audit` |
| 动作预检 | `q3_roadblock(amount=40.0, waybill_id="WB20261105001") -> dict` | `blocked` / `reason_code` / `explain` / `audit` |
| 应用变更 | `apply_change(card: dict) -> dict` | `changed_files`(list) / `code_files`(int) / `restart_required`(bool) |

`audit` 是一个 dict，可携带（**强烈建议**）以下审计要素：

`version` / `rule_id` / `effective_from` / `evidence_ids` / `checksum`

### 数据从哪来

- 数据目录由环境变量 `BENCH_DATA_DIR` 给出（内容见 `data/`）；
- 实现自己的目录由 `BENCH_IMPL_DIR` 给出（**配置副本应放在自己目录里**，这样评测器的
  工作区隔离才生效）；
- 实现**不得**读 `manifest.json` 里的期望值。

## 2. 公平性铁律

1. 所有实现读**同一份数据副本**（`data/` 的逐字节拷贝）；
2. 实现不得读取评测方的期望值（`manifest.json`）；
3. 实现不得 import 评测方仓库里的私有包；**参考实现只依赖标准库**，
   以保证任何第三方都能跑；
4. 变更卡由评测方下发，实现只能通过 `apply_change` 声明自己改了什么；
5. 判定**只看客观值**（数值 + 容差 / 布尔 / 码值），**解释文字不参与判定**。

## 3. 判定口径

| 期望类型 | 判定 |
|---|---|
| 数值 | `|实现值 - 期望值| <= tolerance`（默认 0.01） |
| 布尔 | 相等 |
| 字符串码值 | 相等（大小写敏感） |

用例的全部期望项命中 → 该用例 **PASS**；否则 **FAIL** 并列出每个不匹配项。
一个用例失败**不影响**其他用例的判定——基准要的是分项定位，不是总分。

## 4. 变更卡语义

变更卡在 `data/change_cards.json`。每个变更卡是一次**受控**的业务变更：

| 卡 | 变更 | 考察 |
|---|---|---|
| C1 | 把 4.2 米厢货的免费等候 30 → 20 分钟 | 参数变更后结论是否正确翻转 |
| C2 | 新增 7.6 米厢货费率 | 新增规则维度后能否按新费率算钱 |
| C3 | 把减免上限口径 `actual` → `none` | **同一语义被写两遍**时是否会漂移 |

评测器在应用变更后**总是**重新取一次实现（本体路线 = 重新读声明；属性图路线 = 重启进程）。
两者行为一致；差别体现在 **M1 的 `restart_required` 指标**上。

## 5. 指标定义

| 指标 | 定义 | 怎么算 |
|---|---|---|
| **M1 变更成本** | 一次变更要改几个文件、是否必须重启才生效 | `apply_change` 的返回值 + 实际重载行为 |
| **M2 可审计性** | 答案携带的审计要素个数（0–5） | `audit` 里非空的要素计数（空 `evidence_ids` 不算携带） |
| **M3 一致性风险** | 同一业务语义在实现里被**硬编码**了几遍 | 静态扫描：形如 `X = 30` / `X = "actual"` 的字面量赋值；**从声明读取不算副本** |

## 6. 效度前提（必读）

**本仓库内置的两个参考实现由本仓库作者编写**——因此"属性图路线"这一侧存在**稻草人风险**：
它可能并没有代表一个认真实现的属性图方案。

要让结论成立，必须满足：

- [ ] 属性图路线由**独立第三方**按本协议重写，并通过独立评审；
- [ ] 该实现在**不读取本仓库任何代码**的前提下提交（只需本协议 + `data/`）；
- [ ] 评审记录随提交一起提供。

在此之前，本基准的输出应表述为**"参考实现层面的观察"**，而不是**"本体优于属性图"的结论**。

## 7. 提交与基线

- 评测器用 `--check-baseline` 与 `baseline.json` 比对：任何指标变化都算漂移，退出码非 0；
- 新增用例 / 改期望值 → **必须**同时更新 `manifest.json` 的 `version` 与 `baseline.json`；
- 实现侧提交：把实现放进 `implementations/<your_name>/`，并在 README 的结果表里加一行。

## 8. 已知局限

1. **场景单一**：目前只有货运计费一个微型域，结论的外部效度有限；
2. **审计要素是"有没有"而非"对不对"**：M2 只数携带了几个要素，不校验其内容正确；
3. **M3 是静态近似**：副本计数只认字面量赋值，动态生成或从外部文件读取的副本统计不到；
4. **没有覆盖推理质量**：本基准测的是"声明能不能被正确执行"，不是"模型答得好不好"。
