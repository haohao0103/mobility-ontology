# dbt Semantic Layer 是什么，以及我们和它的真实关系

> 日期：2026-11-23｜依据：dbt 官方文档（Developer Hub）+ 2026 语义层横评 + Fivetran 合并公告
> 结论先说：**dbt Semantic Layer 是"指标语义层"（metrics-as-code）；我们是"对象语义层"（对象+动作+状态机）。
> 两者同一层、不同重心，是上下游关系而非竞争关系。**

## 1. dbt Semantic Layer 是什么

### 一句话

**把"指标定义"从 BI 层搬到 modeling 层，用 YAML 声明出来，由 MetricFlow 引擎编译成 SQL，
让所有下游工具（BI、Excel、Google Sheets、ChatBI、应用）拿到同一个口径的答案。**

### 它解决的具体问题

> 市场部的老王问"上个月活跃用户多少"，技术部的小李查库说 5 万；老王说我算的是 3 万。
> —— 同一个词，两个人指着不同的东西。

dbt Semantic Layer 就是那个"统一翻译官"：**"活跃用户"只许有一个定义**，
且这个定义和 dbt 数据模型放在同一个 Git 仓库里，走同样的 code review、测试、版本控制。

### 它的组成

| 部件 | 作用 |
|---|---|
| **MetricFlow** | 引擎：读语义模型 → 自动处理 join → 编译成 SQL |
| entities / dimensions / metrics | 语义模型的三个基本元素：实体、维度、指标（含派生指标） |
| metrics-as-code | 指标定义是 YAML，与数据模型同仓同 workflow |
| **dbt MCP server** | 让 Claude / ChatGPT 等 AI 直接连语义层 —— "答案用你治理过的指标，而不是去猜原始表" |
| access permissions | 谁能查哪个指标 |
| deploy / materialize / exports / cache | 把指标部署、物化、导出到数仓、缓存加速 |

### 现状（2026）

- **dbt Labs 与 Fivetran 合并已完成**：2025-10 宣布，**2026-06-01 正式完成**；
  George Fraser 继续任 CEO，Tristan Handy 任 President，共同品牌推进"开放数据基础设施"，
  方向是**语义上下文 + 可信 AI Agent**。
- **需付费**：Semantic Layer 属 dbt platform，**要 Starter 或 Enterprise 订阅**（核心引擎 MetricFlow 开源）。
- **横向格局**（2026 Q1 评测）：独立通用语义层里 **Cube**（开源、Headless、MCP 全家桶）是默认推荐，
  **MetricFlow** 是 dbt 用户的延伸首选，AtScale 主打 Excel/重 OLAP，LookML 绑 Looker。
  评测里一句话值得抄：**"MCP 集成度成为新的关键评估维度——AI Agent 时代，
  语义层能否被 LLM 消费是核心竞争力。"**

## 2. 你引的那句话，两处要改

> 原句：「本体=货拉拉的业务语义层……这跟 dbt 的 semantic layer 是同一生态位，
> 我们比它多的是口径互校、来源契约、marking 传播和 AI 圈定。」

| 说法 | 判定 | 修正 |
|---|---|---|
| 同一生态位 | **半对** | 同属"语义层"这一层；但 dbt 的主体是**指标**，我们的主体是**对象与动作** → 更准确是「**同一层、不同重心；且 dbt 在上游**」 |
| 我们多"口径互校" | **对，但要精确** | dbt 的核心能力**恰恰就是口径统一**（一个指标一个定义）。我们多的是**多口径之间的互校**（明细合计 / 声明总额 / 运单快照三者互校）——这是"统一"之上的"互校"，不是"统一"本身 |
| 我们多"来源契约" | **✅ 对** | dbt 有模型级血缘，但没有「**每个费用类型必须恰好被一个连接器认领**，认领缺失/重复/过期/缺证据要显式报出来」这一整套。**这条我们独有** |
| 我们多"marking 传播" | **✅ 对** | dbt 有访问权限（谁能查哪个指标），但**没有"标记随数据流向下游传播"**（行级/列级 → 输出闸门）。这条我们独有 |
| 我们多"**AI 圈定**" | **❌ 不成立** | **dbt 已经做了，而且很靠前**：dbt MCP server 就是把语义图交给 agent，让它用治理过的指标而不是猜表。我们不能宣称独占。**真正的差别是机制**：dbt 是"**把正确的语义提供给 agent**"；我们是"**本体声明直接划定 agent 能看什么、能调什么**"（工具白名单、可圈定类型、证据 checksum）——是**约束强度**，不是有没有 |

## 3. 逐项对比

| 维度 | dbt Semantic Layer | mobility-ontology |
|---|---|---|
| 语义主体 | **指标 + 维度 + 实体**（metrics-as-code） | **对象类型 + 属性 + 链接 + 动作 + 状态机** |
| 产物 | **SQL**（编译到仓库查询） | **可执行结论 + 可执行动作**（写回 / 幂等 / 审计） |
| 语义变更的后果 | 指标定义改 → 全链路刷新（只读） | 本体声明改 → **行为翻转**（包括"从此被拒绝"） |
| 权限 | 访问权限（谁能查哪个指标） | **marking 四级传播 + 行级/列级 + 输出闸门** |
| 数据契约 | 模型测试、schema 契约 | **来源归属唯一 + 缺口四类 + 三口径互校** |
| 审计要素 | 指标定义在 Git 里（有版本） | **答案自带版本/规则ID/生效期/证据/checksum** |
| AI 接入 | **dbt MCP server**（agent 自主检索语义） | **工具白名单由本体裁剪**（agent 无法越界） |
| 写操作 | **无**（只读分析） | 15 动作 + 状态机前置 + 幂等 + 审计 |
| 生态 | **20 万+ 用户、集成遍 BI/Excel/Google Sheets、文档与社区** | 几乎为零 |
| 商业形态 | 需 Starter/Enterprise 订阅 | 自研 |

## 4. 三条结论

### ① 别争"语义层"这个词 —— 争生态我们必输

dbt 有社区、集成、商业化团队、20 年积累；我们在这些上**一比零**。
我们唯一的护城河是**机制**（可执行、可审计、可约束），不是生态。
对外定位不要写"我们是语义层"，要写**"可执行语义层 / 操作语义层"**——
把战场从"谁定义指标"挪到"**谁能把规则变成机器可执行、且出错了能被拦住**"。

### ② 我们的真实差异化有三条，其中一条要改名

| # | 差异化 | dbt 有吗 |
|---|---|---|
| 1 | **可执行**：动作 + 状态机 + 写回 + 幂等 + 审计（改声明 → 行为翻转，含拒绝） | ❌ 完全没有 |
| 2 | **可约束**：marking 四级传播 + 输出闸门 + 来源归属唯一 + 缺口四类 | ❌ 没有（只有访问权限） |
| 3 | **多口径互校**（明细/总额/快照三者互校，而不只是"统一一个口径"） | ⚠️ 部分（它统一口径，但不互校多口径） |

### ③ 互操作是机会，不是威胁 —— 而且现实里两者都要

- **dbt 管"数出来的指标"**（营收、活跃用户）；**我们管"业务对象与动作"**（运单、费用项、改派、减免）。
- 很多企业**两个都要**：问数用 dbt，决策与执行用我们。
- 可做的互操作（成本都不高）：
  1. **dbt metric → 我们的语义层**：把指标声明成"对象类型 + 规则"，复用我们的口径互校与审计要素；
  2. **我们的本体 → dbt**：导出给 BI 消费（我们已有 RDF/OWL 导出通道，SPARQL 侧已通）；
  3. **两边都缺的**：**"问完数之后直接改业务状态"** —— dbt 止步于算出正确的数，
     这一段（动作 + 前置 + 审批 + 审计）只有我们这层有。**这才是我们最该占的位。**

## 5. 一句话对外口径（可直接用）

> 「dbt 的语义层解决的是**指标口径统一**——同一个'营收'在全公司只有一个定义，这是它做得很好的地方。
> 我们做的是**另一层**：把业务规则变成机器可执行、可审计的东西。
> dbt 算出一个数就结束了；我们要回答的是『这个数为什么是它、谁可以改、改了会挡住哪一步、
> 三个月后还能不能复核』。**两者是上下游，不是二选一。**」
