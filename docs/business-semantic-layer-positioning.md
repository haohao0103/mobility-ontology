# 业务语义层定位说明（一页纸）

> 给领导与数据团队的口径：我们建的是什么、解决什么问题、不做什么。
> 数据截至 2026-11-21，全部为实测口径。

## 一句话

**本体 = 货拉拉的业务语义层：在数据不动的前提下，把业务口径声明一次，
全公司查询出准确、可审计、带权限的业务知识。**

类比：数仓解决“数据存在哪”，dbt 语义层解决“营收/完单量怎么算”，
我们解决“**应计多少、谁认领、缺口是什么、谁能看、AI 能问什么**”。

## 解决四个真实痛点

| 痛点 | 现状 | 语义层之后 |
|---|---|---|
| **口径打架** | 同一个“预估运费”，报价单/系统快照/明细表三个数，对账靠人 | 三口径互校是声明的一部分，差异当场归类 |
| **查不准** | “这单为什么贵 38 元”要翻五张表、问三个系统 | 规则声明可求值：等候 53 分钟 → 应计 12 元（规则 R-WAIT-01，版本 3.0.0，生效期 2026-10-01~12-31），超收 13 元当场定位 |
| **说不清** | 数据错了不知道该找谁——没有“谁负责”的声明 | 来源契约：每条费用声明认领方；删一条认领，缺口类型当场暴露（FEE_SOURCE_UNRESOLVED） |
| **不敢用 AI** | 大模型直接读表，把报价 0 元当应计，答“应收 0” | 工具白名单 + 类型圈定 + 证据 checksum：模型只能在本体声明范围内取数，抽掉一条声明即确定性失败（TYPE_UNBOUND），没有降级替身 |

## 与现有体系的关系（不替代，只加层）

```
业务系统（不动） →  数仓/库（不动）  →  【本体声明层（新增）】  →  查询 / 报表 / AI
                                                        口径 · 规则 · 归属 · 权限
```

- **不替换数仓**：数据一行不迁，声明层只读消费；
- **不改业务系统**：零写路径接入，没有“各系统改造”成本；
- **改口径不发版**：改一行 JSON 声明，所有查询路径立即生效——漏改不可能发生（诊断与预检读同一份声明，实测：属性图方案改一处漏一处，诊断说 16.8 元、预检说 12 元且无机制发现）。

## 四个差异化（对标 dbt 语义层 / Palantir 本体）

1. **口径互校**：不只声明“怎么算”，还算“三个口径是否一致”——dbt 只有指标定义，没有互校语义；
2. **来源契约**：“谁认领、缺什么证据、没人认领是异常”是一等语义，不是事后扫描；
3. **marking 传播**：权限从数据源→类→对象→列→Agent 输出全链传播，匿名视角实测 7/9 行可见、Agent 输出 DENIED；
4. **AI 圈定**：本体划定模型能看什么、能算什么，幻觉不靠提示词约束，靠边界划死。

## 诚实的边界（不承诺的）

- **不接管写路径**：动作执行（execute_action 类能力）需要业务系统接入与事务纪律，
  当前明确**不做生产化承诺**，仅在演示中展示“声明被强制执行”的能力；
- **覆盖现状**：500 个类型中 18 个有真实实例数据，缺口如实登记，不做“定义了多少=落地了多少”的美化；
- **非银弹**：声明层解决“知识与口径”，不解决数据采集质量本身。

## 落地路径（三个阶段）

1. **接一个域**：选运费域（现有 47 对象/67 关系已就绪），查询与对账只读接入，出第一份“口径一致性”周报；
2. **治理机制**：1961 属性注册表 + semantic_gate 门禁（声明写错即拦，31 项门禁全绿），声明变更走签字；
3. **扩展**：每接一个新业务域 = 加声明不改代码；退出条件写明——两个季度接不进真实系统即停在演示阶段。

## 一句话记住

> 数仓管数据怎么存，语义层管业务知识怎么算——**改口径不发版、漏改无可能、
> 谁能看是内建属性、AI 有边界**，这就是本体相对“让大模型读表”和“各写各的 SQL”多出来的那一层。
