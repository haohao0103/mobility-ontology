# 500 类 AI 辅助建模推广计划

> 日期：2026-11-25
> 基于：往返验证（`docs/ROUNDTRIP_VALIDATION.md`，8/8 类、53/53 字段保真）+ 方法论 R1–R10
> 原则：**不替换现有 TBox，只加速"新建域/扩充域"的建模；每一步都过人工确认和既有门禁。**

---

## 0. 现状与目标

| 项 | 现状 | 目标 |
|---|---|---|
| 建模方式 | 500 类/503 关系全靠人工写 `C()/L()` | 业务方说话 → AI 出候选 → 校验 → 人工确认 → DSL |
| 建模规范 | 在老建模者脑子里 | R1–R10 显式化、可复查 |
| 质量关卡 | 门禁 + 32 项语义门禁（事后） | 增加校验器（事前）+ 人工确认 why（事中）+ 既有门禁（事后） |
| 多格式导出 | 已有 SHACL/OWL 导出 | 不变，直接复用 |

**核心判断**：不追求"AI 全自动生成 500 类"（那会重蹈 `expand_ontology.py` 复制 540 次凑数字的虚胖覆辙——`build_ontology_v3.py` 注释里已明确反对）。追求的是**AI 出候选、人做判断、门禁做回归**，且每个选择有 why 可回溯。

---

## 1. 三阶段推广

### 阶段 1：盲测校准（先消除开卷偏差）

往返验证是开卷的（生成方看过人工版）。推广前必须做一次 blind test：

- 选 2 个域（建议 `domains_02_capacity` 98类 + `domains_05_infra` 77类），**只给业务方口语描述**，不给字段名；
- 用 `tools/modeling_prompt.md` 让**独立 LLM** 生成候选（生成方不看人工版）；
- 跑校验器 → 与人工版对比，记录真实保真度；
- 通过标准：类召回 ≥ 70%、字段类型准确率 ≥ 85%、状态机合理即可（允许不同切分）。
- 不达标就调 prompt / 补规则，**不进入阶段 2**。

#### ★ 阶段 1 实测结果（2026-11-25，`domains_02_capacity` 98 类）

**结论：不通过 → 按预注册规则不进阶段 2。**

| 指标 | 实测 | 判据 | 结果 |
|---|---|---|---|
| 类召回率（类名精确匹配） | **25.5%**（匹配 25 / 人工 98；LLM 产 113 类） | ≥70% | ❌ |
| 字段类型准确率 | **68.0%**（分母 50 条共同属性） | ≥85% | ❌ |
| 属性召回（辅助） | 26.9%（分母 186 条人工属性） | — | — |

**诊断口径**（不改判据，只回答"未匹配的是不是同一概念换了名字"）：语义对应率
**46.9%**（名称 bigram + 属性集 Jaccard，阈值 0.25）——比精确名高 21pp。

**差距的三个来源**（诊断得出，直接指向下一步）：
1. **命名体系不同**：人工版是**领域约定名**（`VehicleCapacity` 核定载重），
   模型只能给**描述性名**（`CapacityApproval` 载量核定记录）。
2. **粒度更粗**：模型把同主题细类合并（人工的"承运商档案/准入/审核/合同/处罚"
   → 模型的单个"承运商"）。这与 auto-ontology「一表一 Term」的偏好同源。
3. **状态机缺失**：候选格式没有迁移动作（R9 要求状态机完备）→ 提案一律
   `TRANSITIONS_MISSING`，**待人工补**（这是格式缺口，不是模型能力问题）。

**因此 AI 辅助建模的定位要下调**：它是**起草清单**（省掉从零录入，概念覆盖约一半、
属性类型对约 2/3），**不是**能替代人工细粒度建模的清单生成器。

**过程中的两个真实约束（已写进工具链）**：
- **单次输出装不下一个域**：98 类一次性输出会在 JSON 未闭合处被截断（模型本身守规矩，
  是容量不够）→ 工具链改为**两阶段**（A 先类清单 / B 再属性类型），这也是人工建模的顺序。
- **生产 agent 的 `OPENAI_CHAT_STEP_TOKENS=1600`** 对建模场景远远不够；盲测单独放大
  （并在报告里记录该口径）。

### 阶段 2：增量试点（新需求走 AI 流程）

不改动存量 500 类，只对新建模需求试跑：

- 每次新增对象类型时，业务方先写口语描述 → AI 出候选 → 校验器 PASS → 人工确认 why → DSL → 合入 `ontology/domains_XX.py`；
- 记录每次的人工修改量（AI 候选被改了几处），作为质量指标；
- 累计 10 个新增类且人工修改率 < 30% 后，进入阶段 3。

### 阶段 3：存量补强（有选择地重写）

对存量 500 类，**只补不重写**：

- **P2 优先**：给所有带 status 的类补 `OTHER` 兜底态（往返验证发现的真实缺口，R5）——这是机械批量操作，可脚本化；
- **P2 优先**：给所有关系核对基数是否显式声明（R8）——`LEGACY_CARDINALITY` 已补过一批，核对剩余；
- **不做**：不因为"AI 能生成"就重写已有类——那会破坏 rid 稳定性和审计链。

## 2. 成本估算（保守口径）

以本次往返验证为样本：

| 项 | 人工现状 | AI 辅助后 | 依据 |
|---|---|---|---|
| 单类建模耗时 | 约 10–20 分钟（想字段+类型+状态+写 `C()`） | 约 3–5 分钟（写口语描述 + 确认 why） | 往返验证里 8 类的字段/状态从描述一次性产出 |
| 500 类一次性重建 | 约 80–160 小时 | 不建议一次性重建 | 开卷偏差 + 风险，见阶段 3 |
| 新增 1 个域（约 75 类） | 约 12–25 人日 | 约 4–8 人日 | 阶段 2 试点目标 |

**节省的不是"打字时间"，是"从业务语言到建模结构"的转换时间**——这才是建模者真正的脑力开销。

## 3. 风险控制（红线，不许破）

| 风险 | 控制措施 |
|---|---|
| AI 复制凑数（虚胖） | R10 强制每个选择带 why；校验器挡无理由项；`build_ontology_v3.py` 保留结构校验 |
| 字段类型猜错 | R6 硬规则，禁止按名字猜；不确定必须问业务方 |
| 语义错但理由对 | 校验器不判断语义——**Step 5 人工确认不可替代** |
| 破坏 rid 稳定 | R7 身份与可读名分离；改名走 `rid_ledger.json`；不因 AI 生成重写存量 |
| 绕过既有门禁 | AI 候选必须走 `proposal.py` 评审 + `change_gate.py` 签字，与人工建模完全同规 |
| 开卷偏差误判 | 阶段 1 盲测，未过不推广 |

## 5. 立即可以做的三件事（2026-11-25 更新：盲测已做，结论不通过）

1. **候选对齐检查**（把诊断结论工程化，优先级最高）：AI 候选进生产前自动提示
   "这个候选与既有人工类 X 高度相似（属性集/名称相似度高）→ 你是不是要**重复建类**？"
   以及"这里人工有 N 个细类、你合并成 1 个 → 可能需要**拆细**"。做法即 auto-ontology
   `term_families` 的孪生/镜像边识别思路（**从表列集改为类属性集+关系端点**），
   挂在提议通道 `class_add` 的前置校验上。盲测诊断已给出数据支撑：46.9% 的语义对应里
   大量是"已有类的变体"。
2. **补兜底**：按阶段 3 P2，脚本化给所有 status 枚举补 `OTHER`——这是往返验证已确认的
   真实质量缺口，低风险。
3. **判据重新注册**（下一轮，不动本轮）：本轮判据（精确名召回 ≥70%）如实报 FAIL 且**不改**；
   下一轮若要继续投入，用「语义对应率 + 人工改名后命中率」作判据并**事先**预注册阈值——
   看过结果再改口径是自欺。

（"试点"仍在：下一个新增域需求时走一遍
`tools/modeling_prompt.md` → 候选 → `tools/candidate_to_proposals.py` → 提议通道 →
人工确认 why → DSL，记录人工修改率——**这才是 AI 辅助建模的正确用法**。）

## 6. 结论

AI 辅助建模的价值已被往返验证证实（保真 100%，开卷条件），**阶段 1 盲测也已实测**：
未达预注册判据（召回 25.5% < 70%、类型准确率 68% < 85%），诊断显示差距主要在
**命名体系**与**粒度**（概念覆盖约 47%），而非"模型不懂业务"。因此：

- **不进入阶段 2**（AI 自动生成整域类清单）；
- AI 辅助建模的定位 = **起草清单 + 逐项人工改名/拆细/补迁移**，走提议通道（4.0.4），
  由确定性门禁 + 独立裁决者 + 人审兜底；
- 下一个杠杆点是**候选对齐检查**（防重复建类、提示拆细），而不是继续调 prompt 追召回。

方法论已固化成规范，校验器已入库，工具链已打通（盲测 + 接线器 + 提议通道）——剩下的是
用真实新需求试点、用既有门禁兜底。

**不变的红线**：TBox 人工确认、ABox 只读、action 最后、语义门禁 32 项回归——AI 只加速建模输入，不替代判断，不绕过门禁。

**2026-11-25 增补**：AI 候选的**进生产通道**已开通（`freight/proposals.py` 结构层提议
目录 `class_add`/`relation_add`/`group_add_type`，全 t3 人审 + `why`(R10) 必填 + 独立
裁决者）。AI 产出的候选不再只能"给人看"，而是**走提议通道**：确定性门禁 → 独立裁决者
→ 台账 → 人审 → 人改 build 源 → 重 build 出新 pin。AI 候选**永不自动进生产**。
