01 / 四个问题

任何本体，先回答这四件事

不是先讲框架，而是先把一个人群讲透：想圈谁、实际圈了谁、错了会影响谁、谁能改。

1
业务想圈谁？
名称和描述只是弱信号。本体读取结构化意图：车型 LARGE、车贴 ACTIVE、 覆盖 36 个托管城市，来源 structured_intent，置信度 HIGH。
没有建模时：只能按名称猜“大车”，猜错也没有证据。
2
规则实际圈了谁？
规则表达式写的是 vehicle_type = 'SMALL'，城市列表只有 30 个； 绑定的标签是「小车司机」+「车贴已贴」。规则可解析，parse_ok = true。
没有建模时：规则是一段字符串，标签语义和城市范围各查各的。
3
错在哪、会影响谁？
3 个 ERROR：车型相反、标签语义相反、漏 6 个托管城市。 沿下游因果边只算出 6 个影响对象：1 个派生人群、1 个策略、1 个画布、3 个订单。
没有建模时：同城、共享标签都会被算进影响面，真正该止损的订单反而被淹没。
4
谁有权改、怎么留痕？
Agent 只能 propose_change，提议进入 PENDING； 业务人员确认后才执行，全过程写审计日志，不绕过源系统权限。
没有建模时：发现问题靠人，改配置也靠人，改了什么、谁批的无法回放。

03 / 为什么必须先建模

不建模，Agent 只能靠猜

纠错不是写一条 SQL，而是把五个判断依据同时摆到桌面上。缺一个，结论就不可复核。

04 / 核心 Case · 影响面分析

影响面不是邻居列表，是本体声明的因果链

变更只沿 7 条显式因果边向下游传播：Tag → Crowd → Strategy → CanvasTask → Order。 每条边声明方向、起点/终点类型和传播理由；同城、共享标签反向投影、指标、证据、版本、 司机/车辆归属都在白名单外，逐条记入 skipped，不进入资损影响面。

06 / 不是什么

它不是知识库，也不是大模型记忆

把边界说清楚，才能解释为什么结论可复核、写操作必须过人。

不是文档知识库

文档解释概念，但不定义对象 ID、关系方向、状态机和证据链。Agent 读完文档，仍然不知道 36 城从哪来、少了哪 6 个。

不是大模型记忆

模型负责理解问题、选择工具、组织解释，不负责提供事实。每个数字都能回到 HugeGraph 顶点/边和数仓证据。

不是一把 SQL

SQL 能算量级，但不能回答「名称与规则是否一致、会影响谁、改完谁批准」。语义层补的是定义、关系和治理。

也不是“再建一套画像存储”

权威事实仍在画像平台与数仓。语义层只做统一投影、关系与证据回源；写操作回到源系统执行，并保留审计。

07 / 唯一标准

七项都过，才算本体给的答案

页面好看不算数。判定标准是：对象能定位、关系合法、规则可解析、意图可信、冲突可落证据、影响可追溯、变更可治理。

08 / 最小闭环

定义 → 存取 → 执行 → 验收

四段都跑在真实系统上，缺一段就退回“人工拼上下文”。

01 DEFINE

定义

12 类对象、16 条关系、15 条约束、3 个状态机，写在版本化的语义文件里。

02 STORE

存取

HugeGraph 承载时态边；OVERVIEW / NETWORK / FULL 三层投影按任务取上下文。

03 EXECUTE

执行

Agent 只读工具，一次点击只做一次决策或一次查询，不预置链路。

04 ACCEPT

验收

风险等级、冲突项、影响对象和修复建议逐条回源；写操作人工确认。

入口

/profile/ontology
同一个 FastAPI 服务，与工作台、REST API 同源。

运行时

ProfileReasoningAgent
复用 STG 网关；工具全部落在 ProfileService。

治理

propose → confirm → audit
Agent 不直接改资产，权限不绕过源系统。

结论

一个人群能讲清楚，其他人群就能复用同一套判断：先定位对象，再读取结构化意图， 沿关系展开规则与影响，用约束判定冲突，最后把修复动作交给人确认。 画像语义层不是多了一层概念，而是把“业务想圈谁”和“规则实际圈了谁”放进同一张可回源的图里。
